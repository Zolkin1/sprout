# Deployment runtime. Deliberately NO torch: the on-robot path is transfer/deploy, which is
# numpy + onnxruntime only and is tested to keep torch out of sys.modules
# (test_hardware_offline.py). The legacy TorchScript controller that needed it is gone, and
# torch is ~2-3 GB of image for code that would never be imported. casadi went with the MPC.
#
# The GPU wheel, not the CPU one, and PINNED. This pair cannot run on CPU: measured
# step_worst 103.5 ms (27M generator) / 38.8 ms (9.5M) against a 20 ms control period,
# versus 9.8 / 6.0 ms on CUDA. low_level.yml therefore defaults use_cuda: true, and
# resolve_providers raises on a wheel with no CUDA provider -- so a CPU wheel here is a
# bring-up crash, not a slow robot.
#
# ==1.22.0 is not caution, it is a fix: onnxruntime-gpu 1.28.0's [cuda] extra resolves the
# -cu13 wheels and dies at session creation with "libcublasLt.so.13: cannot open shared
# object file" on a CUDA 12.x host. 1.22.0's extras pin nvidia-*-cu12~=12.0 (and cudnn 9),
# which is what this fleet runs. The extras ship the CUDA libraries themselves, which is
# why the image needs no CUDA base and no system CUDA -- tracker_session._preload_gpu_dlls
# puts them on the loader path. Revisit only against a measured box.
#
# onnxruntime-gpu REPLACES onnxruntime -- same `onnxruntime` module, so never both.
#
# NOT INSTALLED HERE ANY MORE -- it moved into an arch-branched RUN in the Dockerfile, because
# which wheel is correct now depends on the architecture:
#
#   x86_64  -- onnxruntime-gpu[cuda,cudnn]==1.22.0, exactly as the rationale above describes.
#   aarch64 -- the plain CPU onnxruntime. PyPI publishes no aarch64 onnxruntime-gpu wheel at
#              ANY version, and the only build that runs on a Jetson Thor (sm_110 needs CUDA
#              13) is cp312 while ROS Humble pins the image to cp310. Two C extensions built
#              for different CPython ABIs cannot share a process, which is precisely why the
#              deploy runtime is being ported to C++. On that architecture the GPU belongs to
#              the C++ runtime at /opt/onnxruntime and the python here is the sim2sim driver
#              and parity oracle only.
#
# The rationale above is kept because it still governs the x86_64 pin.
huggingface_hub      # policy artifact fetch, offline-first (deploy.hardware)

# numpy <2, and it is load-bearing rather than caution. The ROS pinocchio bindings
# (ros-humble-pinocchio, installed in the Dockerfile) are compiled against the numpy 1.x C
# ABI: under 2.x `import pinocchio` prints "AttributeError: _ARRAY_API not found" and then
# SEGFAULTS the interpreter. Measured on this image -- 2.2.6 dies, 1.26.4 imports. The same
# bound is on transfer/requirements.txt for the onnxruntime wheels' ABI, so the two
# environments agree.
numpy<2

# Debug-clip playback ONLY (deploy.clip_reference reads a clip library .h5). Imported
# lazily, so a normal generator run never touches it -- but the mode it enables is the one
# that answers "is this stack wired up at all?", which is worth ~5 MB of image.
h5py

# NOT HERE: the kinematics library. Forward kinematics of the PREDICTED window, for the RViz
# ribbon (deploy.fk, used by g1_control's fm_plan_viz node), is pinocchio -- and pinocchio
# comes from APT (ros-humble-pinocchio, installed in the Dockerfile), not from pip, because
# the C++ controller needs the same package's headers and libraries to FK the depth cameras
# every tick. One install serves both languages; a pip wheel would serve only python and put
# a second copy of the library in the image.
#
# This was `mujoco`, on the argument that the ribbon had to be FK'd on
# FlowMatchingConfig.fk_model_path -- transfer/sim/robots/g1/g1_29j.xml, the model the
# generator's FK loss is defined against -- so that the drawn feet could not become a SECOND
# OPINION about where the feet are. Measured, that is not what the choice buys: over random
# postures the MJCF and the ROS URDF place the four ribbon frames within 4.6e-7 m
# (transfer/deploy/tests/test_fk_parity.py, MuJoCo kept as a test-only oracle). So the image
# no longer carries MuJoCo for a drawing tool, and the robot has one kinematic description.
